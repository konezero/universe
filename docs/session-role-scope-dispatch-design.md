# 세션 Mode · Role · Scope와 작업 배정 설계

- 날짜: 2026-09-10
- 상태: DESIGN DRAFT — 사용자와 논의한 방향을 보존하는 초안
- 범위: 세션 전문성·담당 범위, 공용 작업 큐, 디스패처, Task Frame Boss/Worker 통합
- 비범위: 구현 완료 선언, 실행 권한 부여, 자동 작업 시작, 기존 Registry 변경

## 1. 출발점과 사용자 의도

사용자 설명상 현재는 `Mode ≈ Role`에 가깝다. 앵커의 Node, Mode,
Role, Scope를 활용해 세션별 전문성과 담당을 나누는 것이 확장 방향이다.
현재 저장 스키마와 모든 실행 경로가 아래 구분을 지원한다는 뜻은 아니다.

같은 노드에 여러 MASTER와 CONDUCTOR가 동시에 존재할 수 있다.
예를 들어 한 CONDUCTOR는 사용자와 브레인스토밍하고, 다른 CONDUCTOR는
디스패처 업무를 담당한다. 작업을 단순히 동일 Mode의 기본 세션에 넣는
것만으로는 이 차이를 표현할 수 없다.

Role은 ARCHITECT 같은 고정 직책 enum에 국한하지 않는다.
사용자가 말한 “파이썬의 대가”처럼 전문성, 관점, 일하는 방식이 있는
자연어 페르소나를 표현한다. Scope와 조합해 실제 담당 영역을 정한다.

모델은 턴이 끝나면 스스로 주기적으로 큐를 조회하지 못하므로, 상시 실행
계층이 적합한 작업을 배정하고 세션을 깨워야 한다.

## 2. 개념 분리

아래 필드명은 논리 모델이며 확정된 API/DB 스키마가 아니다.

| 항목 | 의미 | 예시 |
| --- | --- | --- |
| Node | 세션의 소속 프로젝트·노드 좌표 | universe |
| Mode | 기본 활동 틀과 기본 정책 | CONDUCTOR / MASTER |
| Role | 전문성·관점·작업 방식의 페르소나 | 파이썬의 대가 |
| Scope | 담당 프로젝트·기능·문제 영역 | 세션 런타임, 사용자와 방향 탐색 |
| Assignment | 현재 맡은 구체적인 작업 또는 운영 임무 | 회신 누락 진단, 큐 분배·추적 |
| Frame position | 이번 Task Frame에서의 실행 책임 관계 | BOSS / WORKER |

디스패처는 운영 임무이고, 페르소나 Role과 동일한 필드로 고정하지 않는다.
Scope는 담당 범위이지 쓰기 허가가 아니다. Authority, 승인된 실행 범위,
Work Receipt와 Host capability는 별도로 검증한다.

| Mode | Role 예시 | Scope 예시 | 맡는 업무 예시 |
| --- | --- | --- | --- |
| CONDUCTOR | 발상과 탐색에 강한 기획자 | 사용자와 제품 방향 탐색 | 브레인스토밍 |
| CONDUCTOR | 작업 분배에 능숙한 운영 전문가 | 승인된 프로젝트 작업 큐 | 배정 판단·진행 추적·회수 판단 |
| MASTER | 파이썬의 대가 | 지정 프로젝트의 Python 런타임 | Task Frame 책임 또는 구현 |

동일 Node/Mode만으로 세션을 유일하게 식별하거나 배정하지 않는다.
구체적인 배정은 정확한 Session Anchor와 실행 가능한 세션 바인딩에 연결한다.

## 3. 자유로운 Role과 구조화된 배정 정보

자연어 설명을 유지하면서 다음 정보를 구조화하는 방향을 제안한다.

- 표시 이름과 원문 설명
- 전문 분야와 요구 숙련 수준
- 강점, 우선 검토 관점, 피해야 할 패턴
- 기대 산출물과 요구 증거
- 판단 한계와 다른 전문가에게 넘겨야 할 조건

예: “파이썬의 대가”는 Python/asyncio/프로세스 수명 관리 전문성,
동시성 및 소유권 경계 검토, 최소 수정과 회귀 테스트라는 작업 차이로
이어져야 한다. 말투만 바뀌는 페르소나는 충분하지 않다.

LLM은 역할 설명과 작업 요구를 구조화하는 데 사용할 수 있다.
선언된 전문성, Host가 확인한 도구·실행 capability, Bench에서 관측한
성과는 서로 구분한다. 강한 이름만으로 능력, 최고 모델, MAX effort,
실행 권한을 자동 부여하지 않는다.

역할 프로필은 버전으로 참조하고 배정 시 사용한 버전을 기록하는 방안을
검토한다. 실행 중 프로필 수정이 기존 작업의 계약을 조용히 바꾸면 안 된다.

## 4. 공용 큐와 LLM/코드 책임

### 작업 요구

큐 항목은 원본 요청, 프로젝트·노드 범위, 필요한 전문성, 산출물,
검증 조건, 선행 작업, 우선순위, 승인·실행 범위 참조를 가진다.
하위 작업은 원본 작업과 Task Frame lineage를 유지한다.

### 코드 스케줄러

- 큐와 세션 가용 상태를 감시한다.
- 프로젝트·Scope·실행 capability·승인 범위의 필수 조건으로 후보를 거른다.
- 명확한 매칭은 규칙과 관측 성과로 처리한다.
- 배정 소유권, 임대, 시작 ACK, 타임아웃, 회수 상태를 관리한다.
- 배정을 원자적으로 확정한 뒤 기존 실행 경로와 세션버스로 전달한다.

### 디스패처 담당 LLM

- 모호한 작업 요구를 해석하고 적합한 Role/Scope를 제안한다.
- 후보 간 애매한 적합도, 실패 후 재계획, 막힌 의존성을 판단한다.
- 승인 경계를 넘는 범위 확장이나 불명확한 결정을 사용자에게 올린다.

LLM 응답은 배정 후보이지 큐 소유권이나 권한이 아니다. 배정 직전 코드는
가용 상태와 조건을 다시 확인한다. 여러 디스패처가 동시에 판단해도
작업의 확정 배정은 하나의 공통 상태 저장소에서 경쟁을 해결한다.
별도 개인 큐를 만드는 대신 프로젝트·Scope별 공용 큐 조회 범위를 둔다.

## 5. 다중 세션과 실행 수명

세션마다 자동 배정 수신 여부, 가용 상태, 동시 처리 한도를 명시한다.
사용자 대화 담당 세션은 기본적으로 자동 배정에서 제외하는 방향을 제안한다.
실제 값을 어디서 설정하고 누가 변경하는지는 구현 전 확정한다.

작업에는 배정 Anchor, 시도 번호, 임대 소유자·세대·만료, 시작 확인,
결과 참조를 기록한다. 다음은 논리 흐름이며 기존 상태 enum 변경안은 아니다.

```text
대기 → 후보 선택 → 독점 배정 → 전달 → 실제 시작 확인 → 결과 검증 → 완료
                         └ 실패/만료 → 실행 여부 확인 → 재시도 또는 차단
```

- 전달 성공은 실제 시작이 아니다. 시작 ACK와 구분한다.
- 세션이 사라지거나 임대가 만료돼도 실행 여부가 불명확하면 즉시 중복 실행하지 않는다.
- 회신은 작업·시도·배정에 연결하고, 과거 시도의 회신이 새 실행을 완료시키지 못하게 한다.
- 임대만으로 정확히 한 번의 외부 효과가 보장되지는 않는다. 재시도는 효과별
  멱등성, 이전 실행 중단 또는 결과 대조 증거를 필요로 한다.
- 완료된 회신을 다시 회신하며 루프를 만들지 않는다. 후속 작업은 별도 WORK로 생성한다.
- 대기 이유를 EMPTY, 의존성 대기, 사용자 승인 필요, 적합 세션 없음,
  실행 상태 불명확 등으로 구분해 UI에 표시한다.

작업 중복 배정 방지와 파일 충돌 방지는 다르다. 같은 파일을 만지는
서로 다른 작업의 조율·격리 정책은 별도 경계로 유지한다.

## 6. Boss / Worker 통합

Boss/Worker는 세션의 영구 페르소나가 아니라 Task Frame 안의 책임 관계다.
같은 “파이썬의 대가”가 한 프레임에서는 Boss, 다른 프레임에서는 Worker를
맡을 수 있다. 이는 기본적으로 서로 다른 실행 시점/배정을 뜻하며,
한 세션의 동시 다중 작업을 자동 허용한다는 뜻은 아니다.

```text
공용 큐의 상위 작업
  → 디스패처/스케줄러가 적합한 Boss 배정
  → Boss가 Task Frame 하위 작업과 요구 전문성·범위를 선언
  → 공통 스케줄러가 프레임에 바인딩된 Worker 슬롯 배정
  → Worker 결과를 Boss로 회수
  → Boss 검증·통합
  → 상위 작업 결과 검증 및 완료
```

- Boss: 분해, 하위 요청, 진행 조율, 결과 검증·통합에 책임진다.
- Worker: 지정된 한 작업과 입력 계약 안에서 실행하고 증거를 반환한다.
- 스케줄러: 실제 배정·깨우기·가용량 관리와 상태 전이를 담당한다.
- Host: 프로세스·세션 수명과 실제 provider 전달을 담당한다.

Boss가 임의로 provider 세션을 띄우지 않는다. 필요한 Worker를 선언하고
공통 Task Frame 실행 계층에 요청한다. 하위 작업은 프레임 lineage와
할당된 슬롯을 유지하며 범용 WORK 메시지로 Worker 검증을 우회하지 않는다.

Worker 권한은 상위 승인 범위를 넘지 않는다. 재위임은 명시적으로 허용된
프레임에서만 가능하다. 기존 Worker의 읽기 전용 경계나 Boss/Sub Reviewer
지원 범위를 이 문서만으로 확장하지 않는다. 구현 전에 실제 계약을 확인한다.
사용자 대화용 MASTER/CONDUCTOR 세션을 Worker로 재사용할지, 전용 임시
Worker를 쓸지는 격리·수명 정책과 함께 별도로 결정한다.

## 7. 세션버스와의 연결

- WORK: 배정된 작업 전달 및 자동 처리 진입.
- CONVERSATION: 질문·조율. 실행 권한이나 배정 확정을 대신하지 않는다.
- REPLY: 원본 작업 결과 회수와 처리. 큐 완료는 별도 검증 이후 확정한다.
- NOTICE: UI 표시만 수행하며 모델이나 터미널 입력을 건드리지 않는다.

세션버스는 운송 계층이고 큐 상태의 소유자가 아니다. 기존 프로토콜에 대한
문서는 [session-bus-protocol.md](session-bus-protocol.md)를 참조한다.

## 8. 단계별 도입과 확인 기준

1. **현재 구현 조사**: Anchor/Registry의 Role·Scope, 기본 세션 선택,
   Host 폴링, Task Frame claim과 배정 경로를 추적한다.
2. **프로필 분리**: 기존 동작을 유지하며 Mode와 페르소나 Role/Scope를
   분리한다. 같은 Mode의 두 세션이 서로 다른 프로필을 보존하는지 확인한다.
3. **추천 전용 배정**: 작업별 후보와 추천 이유, 제외 사유를 보여준다.
   자동 실행 없이 사용자 대화 세션 제외와 범위 필터를 검증한다.
4. **승인 범위 내 자동 배정**: 큐 → 배정 → 깨우기 → 시작 ACK → 검증을 연결한다.
   다중 디스패처 경쟁, 재시작, 만료, 늦은 회신, 중복 전달을 검증한다.
5. **Boss/Worker 연결**: 기존 Task Frame 경로로 하위 작업을 배정한다.
   프레임/권한 우회 불가와 결과 통합·실패 회수를 검증한다.
6. **LLM 재계획**: 규칙으로 처리할 수 없는 매칭·실패만 디스패처에 올린다.
   예산, 반복 한도, 에스컬레이션과 중지 사유를 검증한다.

스키마 버전, 현재 필드와의 매핑, 마이그레이션 소유자·종료 조건,
프로필 변경 정책, 임대 시간 및 재시도 한도는 구현 전 결정할 항목이다.

## 9. 기존 근거와 이번 초안의 경계

- [Universe Mode Contract](universe-mode-contract.md): 현재 문서의 Mode/Role/Scope
  좌표와 권한 분리. 이 초안이 해당 계약을 자동 변경하지 않는다.
- [Meeting Topic / Role Guide](meeting-topic-role-guide.md): 책임 계약과 역할별
  한계. 회의 모드와 세션의 MASTER/CONDUCTOR 모드는 구분한다.
- RAG 결정 `node-planning-meeting-role-contract` (2026-09-07): 역할을 먼저
  정한 뒤 provider/model을 선택한다.
- RAG 결정 `meeting-role-persona-caliber` (2026-09-07): CPython 코어 기여자급
  전문가 같은 페르소나·숙련 수준, Bench 기반 모델/effort 선택.
- RAG 결정 `universe-conductor-user-delegate` (2026-09-01): Conductor는
  사용자 대리인·조율자이며 승인 경계를 넘지 않는다.

위 RAG 기록은 앞선 조회에서 확인한 관련 근거다. 공용 큐, 다중 디스패처,
앵커별 페르소나 배정 전체가 이미 구현됐다는 증거는 아니다.
이번 저장은 대화의 설계 방향 보존이며, 코드 변경·RAG 채택·작업 실행·
커밋·푸시는 포함하지 않는다.
