## 제품 목표와 사용자 질문

Universe는 프로그래밍에 한정되지 않는 범용 프로젝트 하네스다. Fleet는 프로젝트의 목표와 계획이 어떤 작업으로 실행되고 어떤 결과로 돌아오는지 관찰하는 화면이다. 터미널 목록이나 Worker 수 자체가 목적이 아니다.

사용자는 프로젝트·노드·TODO를 보며 다음 질문에 답할 수 있어야 한다.

- 이 작업은 어떤 목표와 계획 항목을 위해 필요한가?
- 누가 조율하고 누가 실제 수행·검토하는가? 여러 수행자가 있다면 각자 무엇을 맡았는가?
- 지금 무엇을 실행 중이며, 어디까지 확인됐고, 어떤 입력·조건 때문에 기다리는가?
- 실행 결과와 검증 근거는 어디에 있으며, 누가 어떤 근거로 작업 완료를 판단했는가?

사용자가 설명한 원래 ‘세션 창 열기’의 의도는 해당 작업을 수행 중인 Worker들을 보고 선택한 실행을 살펴보는 것이다. 임의의 프로젝트 터미널을 여는 동작으로 대체하지 않는다.

## 현재 구현에서 확인된 차이

`tools/universe_ui/app.js`의 `fleetCardSession()`은 선택한 프로젝트와 project_id가 같은 첫 터미널을 고른다. `openFleetCardSession(todo)`는 그 터미널을 열거나 새 MASTER 세션 생성창을 띄운다. TODO의 수행 배정이나 Worker 실행 식별자를 조회하지 않는다. 따라서 같은 프로젝트에 있다는 이유만으로 담당 세션인 것처럼 보일 수 있다.

현재 Task Frame 소유권·자동화 진단·결과 표시가 일부 구현돼 있으나, 이 사실이 아래 실행 관계 전체의 구현을 뜻하지 않는다. 필드·Action·어댑터 가용성은 후속 구현 시작 시 실제 레지스트리와 저장 계약에서 확인한다.

## 관계 모델의 방향

탐색 흐름은 ‘프로젝트 목표 → 계획 항목 → 노드 → TODO → 실행 시도 → 수행자/검토자 → 결과·근거 → 완료 판단’이다. 이를 항상 한 줄의 트리로 저장한다는 뜻은 아니다. 하나의 TODO에 여러 실행 시도·Worker가 참여하고, 하나의 Task Frame에 여러 TODO가 포함될 수 있다. 공유 실행에서는 TODO별 배정 범위와 결과를 구분한다.

| 대상 | 의미와 소유 경계 |
| --- | --- |
| 프로젝트 목표·계획 | 무엇을 달성하고 어떻게 검증할지. 제안·초안과 채택된 실행 범위를 구분한다. |
| 노드·TODO | 목적·범위·완료 조건·의존 관계. 칸반은 같은 TODO 상태의 표현이다. |
| 실행 시도·Task Frame | 특정 작업 배정, 재시도, 수행·검토의 관계와 근거. 실행은 프로젝트와 Project Master가 소유한다. |
| Master·Boss·Worker·사람·외부 도구 | 조율·수행·검토 등 참여 역할. 공급자나 터미널 존재로 역할을 추측하지 않는다. |
| Host·CLI 세션·관측 스트림 | 실행을 관찰하거나 연결하는 기술 경로. 작업 상태·권한·완료 근거와 별개다. |
| 결과·검증·완료 판단 | 수행 산출물, 검증 결과, TODO 완료 판단을 각각 보존한다. |

기존 안정 식별자를 우선 사용하고 정확한 TODO/Frame/turn/worker_run/결과 참조를 대조한다. 어떤 식별자가 실제로 제공되는지는 계약 조사 후 정한다. 세션 Anchor는 연결 연속성에 활용하되 ephemeral Worker를 영속 Master 좌표로 승격하지 않는다. 프로젝트 첫 세션·최근 활동·시간 근접성만으로 배정을 추정하지 않는다.

## Fleet에서의 경험

TODO 상세의 ‘실행’ 영역은 현재 배정된 실행과 참여자를 먼저 보여준다. Worker마다 역할, 맡은 범위, 실제 진행 근거, 대기·실패 이유, 연결 가능한 관측 수단을 표시한다. Master는 조율자로 구분하고 실행 담당자가 아닐 때 Worker 대신 표시하지 않는다.

여러 Worker는 선택 가능한 목록으로 표현한다. 선택하면 해당 실행에 연결된 터미널·로그·이벤트·산출물을 연다. 모든 실행에 TUI가 있다고 가정하지 않는다. API/ACP/원격 실행은 해당 관측 수단을 사용하고, 없으면 관측 불가 사유와 확보된 근거를 보여준다.

‘미배정’, ‘배정됐으나 시작 전’, ‘실행 중’, ‘입력·의존 작업 대기’, ‘실패’, ‘종료된 실행’, ‘현재 관측 불가’를 구분한다. 이 명칭은 표시 방향이며 새 도메인 enum의 확정이 아니다. Worker가 없으면 ‘실행 중인 Worker 없음’을 표시하고, 직접 Master 수행 등 다른 실행 방식의 실제 연결은 별도로 보여준다. Worker 부재를 작업 실패로 추정하지 않는다.

완료된 실행은 결과와 함께 이력에 남긴다. 과거 실행의 창이 없어져도 근거 탐색은 가능해야 한다. 재시도는 같은 TODO의 별도 실행으로 보존한다. 일반 프로젝트 세션 열기나 새 세션 생성은 별도 명시적 동작이며, TODO 실행 관찰 버튼의 자동 fallback으로 사용하지 않는다.

## 상태와 제어의 공통 원칙

메시지 전달, 큐 접수, provider 턴 시작, Host 생존, Worker 진행, 검증 통과, TODO 완료, 프로젝트 목표 달성을 섞지 않는다. ‘실행 접수’를 ‘작업 중’으로, ‘provider 종료’를 ‘제품 완료’로 올리지 않는다. 상태에는 근거 출처·관측 시각·연결 식별자를 보존하며, 불확실하면 UNKNOWN/미확인으로 표현한다.

Fleet·TODO 상세·칸반·실행 관측 화면은 같은 도메인 projection을 사용한다. UI와 LLM의 조회·지원되는 조작은 공통 Action 계약을 사용한다. 실행 중지·재개·재시도는 수행 상태·권한·어댑터 지원 여부를 검증하는 별도 동작이다. 세션창을 열거나 결과를 보는 행위는 실행 시작 권한이 아니다.

예측은 Galaxy에 두고, 직접 작성한 계획이나 실행 관찰의 필수 입력으로 만들지 않는다. 공동 편집 기능은 별도 프로젝트/보류 범위로 유지한다. 개발용 provider·파일 경로는 범용 작업 모델의 필수 개념이 아니다.

## 후속 구현 순서와 완료 기준

1. 기존 실행 배정·Task Frame·Worker·결과 계약을 조사하고, 각 관계의 실제 소유자와 없는 연결을 문서화한다. 계획 참조 작업과 중복 저장 모델을 만들지 않는다.
2. TODO에서 실행 참여자와 현재/과거 시도를 읽는 공통 projection을 연결한다. 기존 데이터에 연결이 없으면 명시적으로 미연결로 남긴다.
3. Fleet 실행 목록과 실행별 관측 화면 이동을 연결하고 프로젝트 첫 터미널 fallback을 제거한다.
4. UI/API/LLM 조회 결과를 같은 실제 작업에서 대조한다. 구현돼 있는 제어만 노출한다.

완료 검증에는 같은 프로젝트의 무관한 세션, 여러 Worker와 서로 다른 역할, Worker 없는 직접 수행, 종료·재시도, Host 재연결, 관측 불가/오래된 정보가 포함된다. 잘못된 Worker 연결 0건을 식별자 기반으로 확인하고, 수행 성공·검증 통과·TODO 완료를 각각 추적한다. 비개발 사례 한 개로 역할·관측 수단의 범용성을 검증한다. 실 실행과 fixture 검증을 구분하고 NOT_RUN을 완료로 올리지 않는다.
